MG3 and MG4 Memory Usage

Memory Usage for Lossless Encoding

MrSID Generation 3 (MG3) and MrSID Generation 4 (MG4) formats support lossless encoding. The memory usage for a lossless encode operation is roughly given by the sum 

MainMem + TempMem

where 

MainMem = (8 + 4 * SubblockSize + StripHeight) * NumBands * Width * 4


TempMem = 0.005 * (ExpectedOutputFileSize)

and

SubblockSize is set by user (see below)

StripHeight is set by user (see below)

NumBands is the number of bands in the image to be encoded

Width is the width (in pixels) of the image to be encoded

Height is the height (in pixels) of the image to be encoded

WordSize is the number of bytes per sample of the image to be encoded (1 or 2)

We can make some important observations from these formulas. First, the TempMem term has a coefficient of 0.5% and is therefore small enough to be typically ignored. Second, the remaining MainMem term is dependent only on the width of the image, i.e. the height does not matter. (One might choose to think of the image width as defining the "space" required for the encode computation and the image height as defining the "time" required.)

The memory usage is constant over the length of the encode operation.

Subblock Size and Strip Height

The subblock size parameter controls how large the bitplane-encoded regions are. Lowering this parameter may lower the memory usage of the encoder but may also decrease the lossless compress ratio somewhat. Raising this parameter may increase memory usage, but may improve the lossless compression ratio. This parameter has little effect on overall encode time. The default value is 64; typically values range from 32 to 256.

The strip height parameter controls how many rows of the input image are processed at one time. Lowering this parameter may reduce memory usage, but may increase the encoding time. Raising this parameter may increase memory usage, but may also decrease encoding time. Unlike the subblock size, changing parameter will not have any effect on the lossless compression ratio of the output image. The default value is 12; typical values range from 2 to 128. Note that this value must be an even number.

Additionally, the encoder may perform better if the subblock size is a multiple of the strip height.

Given the above default values and given that the memory usage formula contains the sum 

4 * SubblockSize + StripHeight

it is usually more useful to adjust SubblockSize than StripHeight when tuning your memory usage. However, lowering SubblockSize may affect image quality, so care must be taken. Perhaps more importantly, reducing the SubblockSize by a factor four, e.g. from 64 to 16, will increase the number of subblocks in the image by a factor of sixteen: this may result in substantially degraded decode performance.

Example

Assume an image which is 3000 pixels wide by 4000 pixels high, using 8-bit RGB pixels (24-bit color). Assume the strip height is set to 12 and the subblock size is 64. Then,

MainMem = (8 + 4 * 64 + 12) * 3 * 3000 * 4

= 276 * 3 * 3000 * 4

= 9936000

~ 9.9 MB

TempMem = 0.005 * (3000 * 4000 * 3 * 1)

= 0.005 * 36000000

= 180,000

~ 0.2 MB

The encode process should consume about 10MB of memory.

Hints on Tuning Your Encoder

If you have a large image to encode, how should you determine what your strip height and subblock size should be? Follow these steps:

  • First, determine how much physical memory (RAM) your computer has. Typically this will be anywhere from 128MB up to 2GB.
  • Next, start your encode job with the default settings for subblock size and strip height. (Do not run any other jobs in the background.)
  • Open the Windows Task Manager, click the Performance tab, and observe the CPU usage meter. If you are consistently running at between about 85 and 100%, your encode job is at peak efficiency; tuning parameters will not help you.
  • If you are not at peak CPU speed, observe the Physical Memory box at the bottom of the Performance page. The “Total” value should be approximately equal to the amount of RAM you have. (Note that Total is given in K, not MB.) The “Available” value should have plenty of headroom – if it is regularly below 10MB (or 10000K), then the operating system has run out of physical memory and is using virtual memory instead. This means that active data is being paged out to disk, and your encoder is suffering greatly.
  • If you are paging, you can try tuning the encoder parameters. Drop your subblock size down to 32, restart your encode job, and observe the memory utilization again. If you are still paging, consider dropping it down to 24. Going down to 16 might begin to affect image quality for certain images. You can reduce the strip height to 8, 4, or 2 and see if that has any additional impact as well. Ideally you should keep the subblock size at 32 or greater and lower the strip height as much as possible without affecting CPU performance.

Additional hints:

  • If you are reading or writing data across a network, the encoder will probably not be able to run at full CPU speed regardless of your settings. Whenever possible, use local storage.
  • SCSI disk drives will usually give significantly better performance (5-20%) compared to IDE drives.
  • Memory is relatively cheap. Buying more memory is rarely a bad idea.
  • Experienced users can study the performance of the encode process in detail via the Process tab of the Task Manager. Watch for lower CPU utilization, high paging rates, and large virtual memory usage.
  • What kind of an input image are you using? Compressed images, for example JPEG or LZW TIFFs, require additional computation time beyond what the encoder requires for a more “raw” formatted image.
Memory Usage for Encoding, Compressing, and Optimizing

We have 6 modes of operation:

  • E0 encode & pass-through optimizer ("vanilla lossless encode")
  • E1 encode & one-pass optimizer
  • E2 encode & two-pass ("filter") optimizer
  • R0 read MrSID and invoke pass-through optimizer ("no compression")
  • R1 one-pass optimizer
  • R2 two-pass ("filter") optimizer
Heuristic Analysis

For encoding with compression:

if the input file size is less than main memory size, then

use E1

else

if you have enough disk space to store a losslessly compressed image, then

use the preferred method:

  1. do a lossless encode (E0)
  2. then invoke repurposer (R2)

else use the last resort:

use E2. Note: this will require a significant amount of time because it runs the encoder twice

endif

endif

For compressing an MrSID file with the repurposer:

if the MrSID file size is less than 1/2 main memory size, then

use R1 [because R1 will run faster than R2 on small images]

else

use R2

endif

Formal Analysis

Let us assume the following variables:

Fx size of lossless MrSID file

Fr size of input MrSID file (for repurposing)

Mx memory needed to do normal lossless encode

Tx "CPU time" to do normal lossless encode

Q1 O(Npc*Nc*log_2 Nc)

Q2 O(Nc*npc)

Where,

Nc = total number of components in image,

Npc = number planes per component

Ie time to read in the original file (for encoding)

Ir time to read in the input MrSID file (for repurposing) Oc time to write out the compressed file

Then:

E0 cpu time Tx

memory Mx

io time Ie + Oc

E1 cpu time Tx + Q1

memory Mx+Fx+20*Nc

io Ie + Oc

E2 cpu time 2Tx + Q2

memory Mx

io 2Ie + Oc

R0 cpu time (zero)

memory (zero)

io Ir + Oc

R1 cpu time Q1

memory Fr + 20*Nc

io Ir+ Oc

R2 cpu time Q2

memory constant

io 2Ir + Oc

Notes

E1 stores the whole lossless encoded image in memory.

E2 requires two encoding passes, very big time cost but very little memory overhead.

Q1 and Q2 are very small with respect to encoding time and I/O.
